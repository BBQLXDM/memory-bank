# 记忆写入性能优化进化文档

> 记录“几句对话写入很久”这一问题，从排查、定位、分析到解决的全过程。
> 这份文档不是一次性结论，而是持续演进的工作记录：每发现一个瓶颈，就补充一轮分析、改造与验证。

---

## 一、问题现象

### 2026-09-01

在实际写入 C011-C015 的过程中发现：即使一段对话只有几句话，整体记忆写入仍然会花费较长时间，体感上远慢于“文本长度”本身应有的耗时。

典型现象：

- 单个 session 并不长，但 `commit` 仍然耗时明显
- 写入过程并非“卡死”，而是长时间处于模型处理或后端处理阶段
- 即使采用并行，公司之间加速明显，但单家公司内部仍存在较长等待
- 进度面板本身不是瓶颈，真正慢的是写入链路的某些阶段

初步判断：

> 问题不在“几句话”本身，而在“几句话触发的一整套写入链路”。

---

## 二、排查方向

先不把问题死扣在某一个点上，而是从多个角度拆解：

1. **模型推理是否过慢**
   - `commit` 是否在等待 LLM 完成抽取、归纳、纠错、格式化
2. **写入链路是否过于串行**
   - 每个 session 是否都要逐个 `add-message`、`commit`、`verify`
3. **网络往返是否过多**
   - 是否因为多次 HTTP 请求叠加，导致小输入也很慢
4. **验证是否太重**
   - commit 后是否立即轮询查询，造成额外等待
5. **提示词是否过长**
   - 规则和例子是否太多，导致模型输入输出成本高
6. **后端索引/存储是否过重**
   - 主记忆写入时是否还同步做了图谱、共现、embedding 等工作
7. **并发策略是否不足**
   - 是单条本身慢，还是总批次慢

---

## 三、当前已知链路

目前写入过程大致分为：

1. `add-message`
   - 把用户/助手消息逐条送入后端
2. `commit`
   - 触发抽取、总结、生成记忆条目并落库
3. `verify`
   - 再查一次，确认写入是否真的存在
4. 失败时可能还有：
   - seen 记录检查
   - server probe 查询
   - 重试或补写

因此，哪怕只有少量对话，也可能经历：

- 多次 HTTP 往返
- 一次或多次 LLM 推理
- 一次或多次后端落库和索引更新
- 一次 verify 查询
- 必要时再查 seen / 去重 / 补写

这也是“短对话写入仍然慢”的根本背景。

---

## 四、阶段性分析结果

### 4.1 模型推理是高概率瓶颈

写入并不是简单存文本，而是让模型做：

- 关键信息抽取
- 事实归纳
- 冲突识别
- 更正保留旧值
- 记忆格式化
- 多条候选项生成

所以最慢的地方通常不是消息长度，而是 `commit` 阶段的推理成本。

**迹象：**

- `commit` 明显比 `add-message` 慢
- 复杂 session 比简单 session 慢很多
- 有更正、时序对比、多实体的内容更容易慢

---

### 4.2 验证链路也会拖慢总耗时

为了避免假成功，当前流程会在 commit 后做 verify：

- 查询 `items/query`
- 轮询等待确认
- 有时会多次查询

这让写入更稳，但也增加了耗时。

**迹象：**

- commit 已经成功，但验证还在等待
- 单条 session 不长，但整体耗时偏高
- 批量写入时 verify 占用不少总时间

---

### 4.3 索引/附加处理可能同步执行

如果写入主路径里还同步做：

- 共现重建
- 关系图刷新
- embedding 更新
- 二级索引刷新

那主写入自然会被拉慢。

**迹象：**

- 小 session 也慢
- 某些包含多实体的内容明显更慢
- 不同类型的 session 耗时差异很大

---

### 4.4 提示词复杂度可能偏高

如果 prompt 里规则、例子、约束、特殊情况很多，模型每次都要处理大量无关内容。

**迹象：**

- 简短 session 也慢
- 模型输出解释较多
- 输出并不只是记忆条目，还附带很多说明

---

### 4.5 串行策略会放大等待感

即使单个 session 并不算特别慢，如果公司内部完全串行，整体体感会很慢。

**迹象：**

- 同时多家公司时能感觉“批量吞吐”变快
- 单家公司内部仍然一条条等待
- 长 session 会把后面的 session 全部拖住

## 五、已经采取的第一轮改进

### 5.1 公司级并行写入

已经新增：`dev-tools/python/parallel_write_companies.py`

特点：

这一步是为了排查，不是直接提速，但有利于定位。

### 5.3 独立埋点测试工具（不影响现有代码）

新增：`dev-tools/python/profile_write_latency.py`

原则：**所有埋点/测量工作做成独立测试代码，不改动任何现有写入脚本。**

特性：

- 只读 benchmark 数据 + 调用后端 API，**不写 seen 目录、不碰正式输出目录**
- 对每个 session 分别计时：
  - `add-message` 总耗时
  - `commit` 耗时（含 LLM 抽取）
  - `verify` 耗时 与 item 条数
- 输出独立目录：`benchmark-results/profile-latency/<时间戳>/profile.json`
- 支持 `--dry-run`：不发请求，只统计 session 数与对话轮数
- 支持 `--session-limit` / `--sessions` / `--companies` 挑选小样本测量
- 汇总：各阶段平均值/中位数/最小/最大，以及**阶段耗时占比**（add / commit / verify 占总量比例）

用法示例：

```bash
python3 dev-tools/python/profile_write_latency.py \
  --server http://127.0.0.1:8366 \
  --benchmark-dir "/mnt/d/CCBwork/2026/8月/benchmark_v1_0_7/standard/quick" \
  --companies C011 C012 \
  --session-limit 5 \
  --id-prefix zh-memory-v1 --source-client zh-profile-test
```

预期输出片段：

```text
[S001] turns=  5 add=0.2s commit=48.3s verify=0.3s items=4 total=48.8s
[C011] ... add-message 占 0.4%  commit 占 99.1%
```

通过占比可以直观判断：**慢在 commit（模型推理/后端索引）还是慢在网络往返或验证。**

---

### 5.4 第一轮埋点实测结论（2026-09-01，C016 前 3 个 session）

实测数据：

```text
[S001] turns=6  add=6.0s commit=365.8s verify=0.0s items=3 total=371.8s
[S002] turns=6  add=4.4s commit=297.8s verify=0.0s items=5 total=302.3s
[S003] turns=6  add=3.8s commit=482.2s verify=0.0s items=4 total=486.0s

阶段占比（基于平均值）：
  add-message 占 1.2%
  commit      占 98.8%
```

结论：

- **瓶颈 100% 在 commit 阶段**：6 轮对话的 commit 平均 382 秒（5~8 分钟）
- add-message 平均 4.7 秒，verify 平均 0.03 秒——网络与验证都不是问题
- 因此「分级验证」「减少 HTTP 往返」等方向收益极小，可排除
- 待拆解：commit 内部慢在 **LLM 推理** 还是 **后端索引/embedding/多次调用**

结果文件：`benchmark-results/profile-latency/20260901-061327/profile.json`

### 5.6 评测低分复核工具（独立程序）

新增：`dev-tools/python/review_low_scores.py`（不影响现有评测代码）

背景：LLM 裁判对 0/1 分的题可能"压分"（措辞不同即扣分），需要第二意见复核。

判法：**事实点覆盖法**——从预期答案拆关键事实点，逐点核对模型回答覆盖情况，按覆盖率给建议分；复核提示词只喂问题/预期答案/模型回答，不喂原始分与检索结果，避免锚定。

输出目录：`benchmark-results/qa-review/<时间戳>/`

- `review.jsonl`：逐条复核记录（每完成一题立即落盘，中断不丢）
- `review-summary.json`：建议修改数、采纳前后均分/0分率对比
- `review-report.md`：
  - **判低嫌疑清单**：题目名带文档内锚点链接，点击直达明细
  - **逐题复核明细**：保留原内容（问题/预期答案/模型回答/原始评分）+ 是否建议修改 + **修改后评分** + 复核判断 + 原因 + 事实点覆盖情况，每题底部可返回清单

用法：

```bash
# 全量复核（只复核 0/1 分的题）
python3 dev-tools/python/review_low_scores.py \
  --report benchmark-results/qa-evaluation/<run>/report.md \
  --model qwen3.7-plus

# 断点续跑
python3 dev-tools/python/review_low_scores.py \
  --report benchmark-results/qa-evaluation/<run>/report.md \
  --resume benchmark-results/qa-review/<时间戳>

# 不调 LLM，仅根据已有 review.jsonl 重新生成报告（改格式后重刷用）
python3 dev-tools/python/review_low_scores.py \
  --report benchmark-results/qa-evaluation/<run>/report.md \
  --resume benchmark-results/qa-review/<时间戳> \
  --rebuild-report
```

2026-09-07 实测（core 集 20260907-111713 报告）：复核 192 条 0/1 分题，建议修改 148 条，原均分 0.604 → 复核均分 1.052。

**复核后全量总平均分**（2026-09-07 计算，632 题口径）：

| 口径 | 平均分 | 2分 | 1分 | 0分 | 0分率 |
|---|---:|---:|---:|---:|---:|
| 原始评测 | 1.575 | 439 | 116 | 76 | 12.04% |
| A：仅采纳"建议修改"（83 条） | 1.708 | 521 | 36 | 74 | 11.73% |
| B：所有复核分不同都采纳（89 条） | 1.712 | 525 | 30 | 76 | 12.04% |

结论：采纳复核建议后总平均分 **1.575 → 约 1.71**，提升主要来自"措辞不同/直接给出正确数值却被判 1 分"的题修正为 2 分；0 分率基本不变（0 分题多为记忆未写入/检索未命中，复核认可原判）。复核仅修正 1 分压分，不改变 0 分的事实判断。

> 注意：复核的"建议修改数 148"中只有 83 条与原始分实际不同（其余建议分=原分），对总分的影响以这 83 条为主。该总平均分现已集成到脚本汇总输出（见下）。

**复核后全量总平均分已集成到脚本**（2026-09-07）：`review_low_scores.py` 现自动联算评测目录下的 `summary.json` 与复核结果，在 `review-summary.json` 写入 `overall` 字段、在 `review-report.md` 头部渲染"复核后全量总平均分"对比表（原始 / 口径A / 口径B，含分布与 0分率）。

### 5.7 多模态评测启动（2026-09-07，新一周工作）

**数据集**：`data/multimodal/output_v1/`（自服务器 `192.168.100.230` 拉取，tar+scp 约 20MB）

- 20 公司 × 5 session × 5 图 = 100 张 A4 尺寸 PNG（1240×1754，160~220KB）
- 模态三类：`business_profile`（企业档案）/ `credit_summary`（授信摘要）/ `guarantee_letter`（担保函）
- **关键特征：事实只在图片里**——turn 文本仅"确认单已上传"，图片信息含 `extracted_text`（OCR 级金标准，可自动验证入忆）
- QA：普通题 400（factual_recall 246 / temporal_reasoning 88 / abstention 48 / knowledge_update 18，全 easy）+ 图片检索题 100（`image_search_qa_items`）
- 知识更新题天然存在：同一企业档案 2023/2024 版、授信摘要 2023/2025/2026 版跨版本对比
- abstention 题（"图片中未提供该信息"）与现有裁判"正确拒答"规则兼容

**后端能力确认**：`ContentBlock` 支持 text/image（URL 或 base64 源，`ImageBlock`/`Base64Source`），抽取侧有 `MultimodalMetadataNormalizer` 与按内容类型分策略的抽取器——链路具备，缺的是评测侧工具。

**计划**（全部独立程序，`zh-mm-v1` 前缀隔离）：

1. `mm_write_probe.py`：写入探测 + 耗时对比（三组对照：纯文字 / 图文 base64 / 图文+extracted_text 上限参照；产出"图片信息入忆率"与 commit 耗时对比）
2. `mm_eval_qa.py`：多模态问答评测（400 QA + 100 图片检索题，复用现有裁判与低分复核）
3. 结果沉淀进本文档与周记录

已就绪：`mm_probe_data.py`（模拟表格图生成器，验证 image block 协议用；正式探测将直接使用服务器数据集）。

新增：`dev-tools/python/profile_llm_latency.py`（独立测试工具，不发 commit、不写记忆）

目的：判断 commit 的 5~8 分钟是否来自**模型推理本身**。

四个场景由轻到重：

| 场景 | 说明 | 判读 |
|---|---|---|
| ping | 最小请求 | 基础延迟（正常应 <10s） |
| short_out | 短输入+中等输出 | 简单抽取耗时 |
| long_input | 长输入+结构化输出 | 模拟 6 轮对话 + 抽取 prompt |
| long_output | 中等输入+长输出 | 模拟多条记忆条目生成 |

用法：

```bash
python3 dev-tools/python/profile_llm_latency.py --rounds 2
# 可选：--model qwen-plus 覆盖模型、--rounds 3 多次测量
```

结果写入：`benchmark-results/profile-latency/llm-latency.json`

判读逻辑：

- **long_input 场景也要 3~6 分钟** → 瓶颈在 LLM 推理本身（换模型/精简 prompt/分级抽取）
- **所有场景都快（几秒~几十秒）** → 瓶颈在后端 commit 内部（多次 LLM 调用/索引/embedding/共现重建），需进一步拆后端

## 六、后续解决方案路线

### 6.1 跑耗时埋点（工具已就绪，待执行）

埋点工具已独立就绪：`dev-tools/python/profile_write_latency.py`（见 5.3）。

执行步骤：

1. 在正式写入前，先抽 1~2 家公司、每家公司 3~5 个 session 跑埋点
2. 查看输出占比：commit 是否占 95%+，确认瓶颈环节
3. 把 profile.json 与分析结论补记到本文档第七节前后

---

### 6.2 分级验证

不是所有场景都必须“写完立刻强 verify”。

建议分层：

- **调试/补写模式**：强 verify
- **正式批量模式**：抽样 verify 或延迟 verify
- **高成功率公司**：减少重复确认

这样能减少验证本身的耗时。

---

### 6.3 拆分主写入和附加索引

如果 commit 里包含：

- 关系图更新
- 共现重建
- 二级索引刷新

建议把它们异步化，主路径只保证基础记忆先落库。

目标：

- 主写入先快
- 辅助索引后台补
- 失败时不阻塞主流程

---

### 6.4 精简 prompt

建议把提示词分层：

- 基础抽取规则
- 特殊更正规则
- 复杂时序规则

简单 session 不必承担完整长 prompt 的成本。

---

### 6.5 进一步优化并发策略

当前已做到：

- 公司间并行
- 公司内串行

下一步可以观察：

- 并发度 2、3、4 哪个最稳
- 哪些公司容易触发慢请求
- 是否需要按 session 大小动态分配 worker

---

## 七、当前结论

目前的初步结论是：

> “几句对话写入很久”通常不是文本量问题，而是写入链路中的 LLM 推理、验证、索引更新、HTTP 往返、串行调度共同叠加造成的。

所以优化顺序建议是：

1. **先量化耗时**
2. **再分层拆解瓶颈**
3. **再优化验证和索引**
4. **最后继续优化并发和 prompt**
